# Decision log

Technical decisions made during the build, newest first. Each entry has the date, the decision and a one-line reason. Product decisions are in `build-brief.md`.

| Date | Decision | Reason |
|---|---|---|
| 2026-11-18 | Environment entries for Supabase are named `SUPABASE_PUBLISHABLE_KEY` and `SUPABASE_SECRET_KEY`, replacing the anon and service-role names | The project is on the new key types, and under the old names the two values had been entered the wrong way round |
| 2026-11-18 | News launches with the wide outlet set, without the New York Times and Nature (the owner's choice) | Those two publishers' terms lean against a shared app; the rest are personal-use and unclear (spike 12) |
| 2026-11-18 | News is publisher RSS only at launch; a news API (GNews free tier) is added only when a person picks a topic no feed covers | All 20 working feeds give headline, link and date at no cost; NewsAPI.org's free plan forbids production use and GDELT failed every live request (spike 12) |
| 2026-11-18 | News items store headline, link, outlet, date, section and tags only; article text and images in feeds are discarded on arrival | The brief shows headline, outlet and link, and several publishers bar storing more (spike 12) |
| 2026-11-18 | News is shown with headline and link exactly as supplied and the outlet named, kept seven days, with a per-source off switch | Meets the strictest explicit publisher conditions and lets one outlet be removed on request (spike 12) |
| 2026-11-17 | Papers launch with arXiv daily category feeds, then bioRxiv and medRxiv, then OpenAlex with a free key; Semantic Scholar is held back | arXiv abstracts are CC0; Semantic Scholar has two live licence pages that disagree (spike 13) |
| 2026-11-17 | A bioRxiv or medRxiv preprint with no reuse licence is shown without its abstract | The source's terms are unclear for those items (spike 13) |
| 2026-11-17 | Papers are stored once in a shared table and de-duplicated by normalised DOI and arXiv id | One nightly fetch serves everyone; the DOI is the common key (spike 13) |
| 2026-11-17 | Poetry is PoetryDB imported once into the app's own table, limited to poets who died by 1930 unless a source shows earlier publication, with the CC BY credit shown | The licence permits copying; the import removes a nightly dependency on a one-person service (spike 11) |
| 2026-11-17 | Web push is a best-effort nudge that opens the app; nothing that must be seen is sent by push alone, and anything needing a tap to answer goes to Telegram or the app | iOS has no notification action buttons and no measured delivery rate; four subscription-loss bugs are open (spike 4) |
| 2026-11-17 | Web push uses Declarative Web Push with a service-worker fallback; the app re-checks its subscription on every open | Declarative push avoids the silent-push penalty and survives storage clean-up; WebKit sends no subscription-change event (spike 4) |
| 2026-11-17 | Sessions are stored in cookies, not browser storage | Cookies are the only thing copied when a page is added to the iPhone Home Screen (spike 4) |
| 2026-11-17 | Telegram is linked by a single-use, short-lived token in a `t.me/<bot>?start=` link opened from the app; a blocked or unlinked bot falls back to the in-app thread | A bot cannot message anyone who has not started it (spike 5) |
| 2026-11-17 | Telegram webhook verifies the secret header, queues the update and returns; buttons carry a short opaque id and are acknowledged at once, then removed | Callback data is capped at 64 bytes and taps must be answered within seconds (spike 5) |
| 2026-11-17 | Every outgoing message records a lane (capture, reminder, digest) whether or not Telegram topics are switched on | Lets the one-thread-or-three-lanes choice change without rework (spike 5) |
| 2026-11-17 | The published calendar feed is treated as a next-day channel; same-day changes go through the app and the message queue | Apple and Google publish no refresh interval for subscribed feeds (spike 7) |
| 2026-11-17 | The feed sends refresh hints, supports conditional requests and records the time and client of each fetch, with no content | Gives each person, and us, the refresh measurement Apple does not publish (spike 7) |
| 2026-11-17 | For Google Calendar (step 11): publish the Google project as "In production" and unverified, never "Testing", with the narrowest write scope | No Calendar scope is restricted, so no paid assessment; only "Testing" expires tokens after seven days (spike 7) |
| 2026-11-17 | Intake address is a long random token under one catch-all rule; the token is the only thing authenticated; the sender is shown as claimed, never as verified | Sender identity cannot be proven after forwarding (spike 6) |
| 2026-11-17 | The email Worker checks the token, stores the raw message encrypted, queues it and returns; parsing runs in the job runner | Workers free plan allows 10 ms of processor time (spike 6) |
| 2026-11-17 | Setup shows Gmail's forwarding confirmation code and confirm link for the person to tap; the app never opens it and never shows the cancel link | Acting on a link found in mail would be acting on untrusted content (spike 6) |
| 2026-11-17 | Setup includes an end-to-end test message, and the intake page says some strict senders' mail will not survive an automatic forward | Cloudflare rejects mail failing SPF and DKIM, or DMARC, before the Worker runs (spike 6) |
| 2026-11-17 | Extraction runs on Claude Haiku 5.5 at medium effort, fixed output format, no tools, no memory, with a random boundary tag around the email | Measured: 34 of 34 hostile emails left the record unaltered, 26 of 28 ordinary emails fully right, $0.00031 each (spike 8) |
| 2026-11-17 | Routing never reads the model's confidence; it reads consequence and code checks only | The model reported high confidence on every wrong record (spike 8) |
| 2026-11-17 | A record the model flags as containing instructions always goes to the staging inbox; a call that returns no record keeps the raw item and files a "could not read this" entry | Fail towards the person seeing it; an item is never dropped (spike 8) |
| 2026-11-17 | Extracted text fields are still untrusted when the planning agent reads them later, and are passed as quoted data | The extraction step cannot stop a sender planting words for a later reader (spike 8) |
| 2026-11-17 | Sign-in is a native Supabase passkey day to day, with an emailed six-digit code (not a link) for first sign-in, new devices and recovery | A link opens in Safari, not the Home Screen app, and mail scanners can use it up (spike 9) |
| 2026-11-17 | Passkey calls live in one module with the client library version pinned, and the code path always works | Supabase labels passkeys experimental and may change the API (spike 9) |
| 2026-11-17 | Sign-up is off; accounts come only from server-side invites; a "before user created" hook re-checks the invite table | Two independent gates on a closed group (spike 9) |
| 2026-11-17 | Prices are an effective-dated table in the database; the spend meter multiplies each response's reported token counts by it and never estimates | Prices change and differ by model, cache use and prompt length (spike 10) |
| 2026-11-17 | Default models: Haiku 5.5 for extraction and consolidation, Sonnet 5.5 for planning and chat, Opus 5.5 for weekly review; Fable 5.2 offered, not default | Matches the brief's cheapest, mid-tier and larger routing at current prices (spike 10) |
| 2026-11-17 | Nightly consolidation uses the Batch API | Half price, and available because each person pays with their own key (spikes 1, 10) |
| 2026-11-17 | Application-level envelope encryption: one top key in a key service, one data key per person stored wrapped, AES-256-GCM in application code with each value bound to its person, table, column and row | Prototype passed 25 of 25 isolation checks; Supabase advises against pgsodium, and Vault is readable by the service role (spike 3) |
| 2026-11-17 | The worker reaches people's data only inside one transaction scoped to one person as the `authenticated` role; the service-role key is not in the worker's environment | Row-level security then applies to the worker exactly as to a signed-in person (spike 3) |
| 2026-11-17 | The single cross-person query is one function that returns due person ids and nothing else | The dispatcher must ask who is due; this keeps "no query may read across users" true for content (spike 3) |
| 2026-11-17 | The worker's key-service credential can only unwrap and its database login cannot bypass row-level security | Trigger.dev disclosed on 1 November 2026 that environment variables were read for some customers (spikes 2, 3) |
| 2026-11-17 | Key service is AWS KMS at about $1.21 a month (approved by the owner on 2026-11-18) | Native encryption context, unwrap-only permissions and a request log (spike 3) |
| 2026-11-17 | Every table ships with a cross-person denial test, plus one schema-wide test that fails if any table lacks forced row-level security | Makes the hard constraint mechanical (spike 3) |
| 2026-11-17 | Use Supabase's new publishable and secret keys from the start | The `anon` and `service_role` keys are being retired at the end of 2026 (spike 3) |
| 2026-11-17 | Stay on Trigger.dev's free plan; the every-minute tick comes from a Cloudflare Worker cron trigger that asks Postgres who is due and starts one run per person | The free plan rejects schedules faster than hourly; this keeps the dispatcher pattern at no cost (spike 2) |
| 2026-11-17 | "Due" is a database question, runs carry an idempotency key of person, job type and scheduled time, and Postgres holds the queue | A missed or repeated tick heals itself, and a rejected run is not lost (spike 2) |
| 2026-11-17 | Job payloads and outputs carry ids and statuses only; content is fetched and decrypted inside the run | Trigger.dev stores payloads and shows them in its dashboard (spike 2) |
| 2026-11-17 | Launch on each person's own API key, encrypted with their data key; linked billing sits behind the same "who pays" interface for later | Linked billing is capped at 10 people without an Anthropic review and still needs each person to fund a Console organisation (spike 1) |
| 2026-11-17 | Specification and research committed; build starts with the spikes in the brief | Several stack choices rest on points not yet verified |
